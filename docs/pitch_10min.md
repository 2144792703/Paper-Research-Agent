## 1. 背景与动机（1 分钟）

我要解决的是「把一堆论文摘要变成一份能复核的中文综述」。手工流程是：搜主题、逐篇读摘要、挑重点、拼综述、自己检查有没有编数据，一轮几个小时，而且质量取决于当天状态。

现有工具的问题是断层：检索工具只给列表，摘要工具只给单篇总结，聊天式 Agent 又不给结构化的评审记录。所以我把目标定成一条可观测的流水线：输入主题和篇数，输出固定三段式报告（研究背景 / 论文对比 / 研究空白），同时给出评审意见、追问方向和数字校验结果。

边界我也提前划了：只读 arXiv 摘要，不做 PDF 全文解析，不做引用排版，`followup` 只给方向建议，不是多轮对话。这样做的代价是结论受摘要信息量限制，好处是链路短、每一段都可验证。

## 2. 架构与数据流（3 分钟）

整张图 7 个节点：`supervisor → search → select → summarize_one → summarize → critic → followup`，用 `StateGraph` 编译，状态是 `SupervisorState` 这个 TypedDict。

主链路是固定边：`search → select → summarize_one → supervisor`，以及 `summarize → supervisor`。真正的分叉只有两处条件边：

第一处是 `supervisor` 的 `route`，按 `state["next"]` 分发到 `search / summarize / critic / end`。
第二处是 `critic` 之后的 `after_critic`：`critique` 等于「通过」或者 `revision_count >= critique_times` 就进 `followup`，否则回 `supervisor` 再审一轮。

这里有两个关键设计。

一是 `supervisor` 并不是每次都调模型。只要已有综述，就直接按「上次是否刚评审」返回 `summarize` 或 `critic`；只要有论文但没综述，就直接返回 `summarize`。只有初始状态才把状态表交给 cheap 模型判定，同时负责识别乱码主题。这样既省钱，也避免模型抖动把路由判成环。代价是路由的「智能」被刻意限制成状态机，灵活性换确定性。

二是多重终止保障：`revision_count` 每次评审加 1，`critique_times` 是用户给的轮数上限（默认 2）；连续 `MAX_SEARCH_ATTEMPTS`（默认 3）次搜索为空直接 `end`；外层还有 `RECURSION_LIMIT=60` 兜底，防止条件边意外成环。所以这套图不会无限跑。

一次典型运行（5 篇论文、评审 2 轮）是 12 次 LLM 调用：初始路由 1 次、筛选 1 次、单篇总结 5 次、综述 2 次、评审 2 次、追问 1 次。这个数字可以直接和终端统计对上。

## 3. 关键设计决策（3 分钟）

**模型分级。** 高频、短输出的节点用 cheap：`supervisor`、`select`、`summarize_one`、`followup`；决定最终质量的 `summarize` 和 `critic` 用 strong。远程模式下如果 cheap 和 strong 不是同一个模型，会自动给 cheap 加 `enable_thinking=false`，避免轻量模型把预算花在思考上。

**缓存。** 缓存键是 `sha256(CACHE_VERSION + provider + model + temperature + top_p + 规范化 prompt)`，provider 段在 remote 下带 `BASE_URL` 指纹，换服务地址不会串缓存。有两个细节：空响应不写入缓存，读取时遇到历史空值会删除并视为未命中；思考与非思考模式的键额外加 `|no-think` 隔离。缓存命中不发请求、不计 token，也不产生 Langfuse Generation。代价是代码逻辑变化覆盖不到，需要手动提升 `CACHE_VERSION`。

**三层兜底。** 路由失败或空输出，走 `_fallback_route` 的确定性状态表；筛选失败或 JSON 解析失败，按搜索顺序保留前 N 篇；综述失败或空响应，用已完成的结构化摘要拼简版 Markdown。另外单篇总结失败保留空结构，评审失败按「通过」处理但不阻断，追问失败给占位提示。原则是：非关键路径降级，关键路径不中断。

**key 池与限流。** 429 按 `KEY_COOLDOWN × 2^(n-1)` 退避、封顶 60 秒后换 key；5xx 和网络错误固定冷却 5 秒后换 key；401/403 直接把该 key 永久禁用；最多遍历 4 轮。全局还有可选的 RPM 滑动窗口，默认 10 次/分钟，所有 key 共享。

**混沌与观测。** `CHAOS_FAILURE_RATE` 在请求发出前按概率抛一个继承自 `APITimeoutError` 的异常，复用现成的换 key、退避、重试和兜底链路，业务节点零改动。Langfuse 是双 key 齐全即启用，`graph.invoke` 注入 CallbackHandler 后，一次研究是一条 Trace，每个节点是 Span，每次真实调用是 Generation，缓存命中不产生 Generation。

## 4. 难点与踩坑（1 分 30 秒）

第一个坑最典型：模型返回空串，被写进缓存，下次命中又拿到空综述，`supervisor` 就一直要求重写，几乎死循环。修法是三层：空响应不写缓存、读取时删除历史空值、路由加确定性护栏，再加综述兜底。

第二个坑是 Windows 下的磁盘缓存文件锁：`.cache/cache.db` 被进程占用时删不掉，所以清缓存统一走 `python main.py --clear-cache`，README 里也写明了。

第三个是单 key 限流边界：免费额度下 429 很频繁，单 key 在 4 轮遍历内可能耗尽；多 key 池能平滑，但整体吞吐仍受 RPM 限制，所以后来加了全局滑动窗口。

第四个是评审的精确匹配：「通过」判定原来用 `critique.strip() == "通过"`，模型输出「通过。」就会多跑一轮综述和评审。截图里 12 次调用的运行就是 2 轮评审，而不是 1 轮。现在已改成去尾标点再比较，并在 `tests/graph_test.py` 补了回归用例。

## 5. 量化成果（1 分钟）

- 单篇总结并发化：并发度 3，总结阶段 102.19 秒降到 29.43 秒，提速 3.47 倍；同一次对比里整轮耗时 192.48 秒降到 123.33 秒。
- 5 篇论文一次完整运行：12 次 LLM 调用，input 4988 / output 3470 / total 8458 tokens。
- 缓存二次命中：同一主题第二次运行 182.20 秒降到 1.41 秒，hit 12 / miss 0，token 为 0，因为完全没有发请求。
- 测试：48 个离线用例全绿、5 个 live 用例默认排除；覆盖混沌与三层兜底、缓存键隔离、服务端 SSE 事件、数字校验误报回归。
- 成本口径：按模型分别乘输入/输出单价；价格表查不到的模型只报 token，不硬算金额，避免给出假数字。

## 6. 可改进方向（30 秒）

第一，补全在用的 Qwen 模型单价，让成本统计从「只报 token」变成可计价。第二，把 SSE 从「开始/终态」扩展成节点级进度。第三，接 checkpointer 做任务持久化，并把 `followup` 做成真正的多轮研究。降级质量标记已经落地：任一兜底触发都会写入 `degraded / degraded_reasons`，CLI 和 SSE 都会返回。
